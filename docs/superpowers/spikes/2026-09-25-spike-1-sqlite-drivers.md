# SPIKE-1: SQLite drivers through Drizzle

Date: 2026-09-25. Spec §1.1 blocks M0 on one question: does `drizzle-orm/sqlite-proxy` work on `node:sqlite` and `sql.js`?

Reproduce with `packages/database/spike/conformance.mjs`:
- `node spike/conformance.mjs <driver>`
- `bun spike/conformance.mjs bun-sqlite[-locked]`

Versions:
- `drizzle-orm` 0.45.3, `drizzle-kit` 0.31.11
- `better-sqlite3` 13.0.3, `sql.js` 1.14.2
- Node 22.19.0 and 24.21.0, Bun 1.3.14, all on Windows x64

## What "works" means

Each driver ran the same checks against a temporary file database. The schema has text, integer, boolean-mode, and JSON-mode columns plus a foreign key. The migration was generated by `drizzle-kit`.

The checks:
- migration, run twice
- insert with `returning`, and JSON and boolean round-trips
- update and delete
- a SQL `sum ... group by`
- `batch`, and a `batch` that must roll back entirely when one statement fails
- transaction commit, and rollback on throw
- an async transaction callback
- two isolation checks:
  - a write issued outside an open transaction must survive that transaction's rollback
  - two concurrent transactions
- persistence after close and reopen

The isolation checks exist because 9router depends on atomic transactions for OAuth token merges and usage writes. It relies on the fact that "better-sqlite3 is sync → no JS yield mid-transaction → no race" (`usageRepo.js:255`).

## Results

| Check | better-sqlite3 | bun-sqlite | sql-js | node:sqlite via proxy | all four via locked proxy |
|---|---|---|---|---|---|
| migrate, CRUD, JSON/boolean, aggregate, commit, rollback | pass | pass | pass | pass | pass |
| `batch` | unavailable | unavailable | unavailable | pass | pass |
| failed `batch` rolls back entirely | unavailable | unavailable | unavailable | **fail** | pass |
| async transaction callback | rejected | accepted | accepted | pass | pass |
| outside write survives a rolled-back transaction | fail | **fail** | **fail** | **fail — outside write rolled back** | pass |
| two concurrent transactions | fail | pass¹ | pass¹ | **fail — `Failed query: begin`** | pass |
| persistence after reopen | pass | pass | pass | **fail — rows lost** | pass |

¹ Passing only because the callback never really ran inside the transaction. See the second finding.

On Node 24.21.0, the locked variants of better-sqlite3, node:sqlite, and sql.js each passed 12/12. Bun has no Node 24 run.

To show the lock is doing the work, I broke it on purpose: statements no longer waited for an open transaction. The "outside write survives" check then failed.

## Findings

1. **`sqlite-proxy` alone is unsafe under concurrency.** Every statement shares one connection. A statement issued while an async transaction is open joins that transaction:
   - An unrelated write can be rolled back with someone else's failure.
   - A second `begin` fails.
   - A transaction left open by that failure loses rows on close.
   - Proxy `batch` is also not atomic unless the batch callback wraps it.
2. **Sync drivers cannot run async transactions safely.**
   - better-sqlite3 rejects them, but only after the callback's synchronous part has already run.
   - bun-sqlite and native sql-js accept them silently and commit before the awaited statements run, so atomicity is lost with no error.
   - Repository code therefore cannot mix native sync drivers with the async proxy. One transaction style must cover all drivers.
3. **All four underlying clients are synchronous.** The fix is one per-database lock in front of `sqlite-proxy`:
   - A transaction owns the connection from `begin` to `commit`.
   - Statements inside it, tracked with `AsyncLocalStorage`, run immediately. Everything else waits.
   - `batch` runs inside `BEGIN/COMMIT`.

   With the lock, all four drivers pass every check through the same async API, the same `db` type, and the same migrator.
4. **Drizzle 0.45 ships a native `sql-js` driver.** The spec assumed sql.js needed the proxy. Because of finding 2, routing it through the locked proxy is still the safer choice.
5. **better-sqlite3 13 bundles N-API prebuilds** (including `win32-x64.node`) and needs no build tool.
   - Allowing its install script makes pnpm run an implicit `node-gyp rebuild`. That failed here without Visual Studio.
   - `pnpm-workspace.yaml` therefore denies its build: `allowBuilds: false` for pnpm 12, `ignoredBuiltDependencies` for pnpm 10.
   - It loaded under both pnpm versions.
   - 9router's comment that better-sqlite3 segfaults on Node ≥ 24 does not hold for v13 on 24.21.

## Recommendation

SPIKE-1 passes, but with a design change from spec §1. The spec says to use native drivers for `bun:sqlite` and `better-sqlite3`, and `sqlite-proxy` for `node:sqlite` and `sql.js`. Instead, **route all four clients through one locked `sqlite-proxy` wrapper**. Keep the driver order: bun:sqlite on Bun; on Node, better-sqlite3, then node:sqlite, then sql.js.

Costs and ceilings to accept:
- All access to one database file is serialized in-process. SQLite already has a single writer. Each synchronous statement is short, but an `await` on network I/O inside a transaction would block every other query, so transactions must not do I/O.
- Calling `db.transaction` inside another transaction would issue a second `begin`, which the spike's concurrent-`begin` failure suggests will fail. This was not tested directly. Nested work should use `tx.transaction`.
- sql.js lives in memory. The spike exports the file only on close. The real driver needs a persistence policy, such as export after each write with a debounce and on shutdown. That policy sets how much data a crash can lose.

Before `packages/database` is built on this design, confirm the change to spec §1, because it replaces a locked decision.
